# B3-1 Glossary · 아키텍처를 읽기 위한 용어 사전

이 미션은 **외부에서 접속 가능한 웹 서버를 만들고, 접근을 제한하며, 동작과 정리까지 증명하는 실습**이다.

처음에는 다음 한 문장으로 이해하면 된다.

> 방문자가 EC2라는 빌린 컴퓨터로 요청하면, IGW라는 인터넷 출입구를 지나 SG의 허용 규칙을 확인받고, Nginx가 웹 응답을 보낸다.

아키텍처 이미지: [architecture.png](architecture.png) · 설계 설명: [architecture-design.md](architecture-design.md)

## 1. 그림의 네 가지 색

| 번호·색 | 흐름 | 누가 시작하는가? | 무엇을 하는가? |
| --- | --- | --- | --- |
| 01 파랑 | 웹 요청 | 방문자 | 웹페이지나 서버 상태를 요청 |
| 02 초록 | 웹 응답 | 요청을 받은 웹 서버 | 상태 코드와 응답 본문을 방문자에게 반환 |
| 03 보라 | 서버 관리 | 운영자 | SSH로 로그인해 서버 점검·설정 |
| 04 주황 | 외부 통신 | EC2의 프로그램 | 패키지 다운로드 등 외부 서비스에 요청 |

02는 01에 대한 답장이다. 04는 서버가 새로 시작하는 통신이며, 그 요청에도 외부 서비스의 답장이 돌아온다. 실선 화살표는 통신 방향, 회색 점선은 설정의 적용 관계다. 선이 교차한다고 연결된 것은 아니다.

## 2. 컴퓨터와 프로그램

### EC2 · 이씨투 · Elastic Compute Cloud

- **쉽게:** AWS에서 빌리는 컴퓨터.
- **정확히:** 운영체제와 프로그램을 실행하는 가상 서버를 제공하는 AWS 서비스.
- **이 과제:** Linux 서버 1대에 Nginx를 실행한다.
- **구분:** EC2는 컴퓨터이고 Nginx는 그 안에서 실행되는 프로그램이다.

### Instance · 인스턴스

- **쉽게:** 실제로 만들어 놓은 컴퓨터 한 대.
- **정확히:** EC2에서 생성한 개별 가상 서버. 고유한 인스턴스 ID가 있다.
- **예:** `i-...`는 개별 인스턴스 식별자이고, micro는 크기를 나타내는 유형의 일부다.

### Nginx · 엔진엑스

- **쉽게:** 웹 요청을 받고 페이지를 돌려주는 안내 직원.
- **정확히:** HTTP 요청을 처리하는 웹 서버 소프트웨어. 프록시 등으로도 쓸 수 있다.
- **이 과제:** `/`에는 웹페이지, `/health`에는 정해진 상태 응답을 제공한다.
- **구분:** Nginx가 EC2를 만드는 것도, SSH 로그인을 처리하는 것도 아니다.

### Process / Listening · 프로세스 / 리스닝

- **쉽게:** 프로그램이 일하는 중인지, 요청받을 문을 열고 기다리는지.
- **정확히:** 프로세스는 실행 중인 프로그램이며, 리스닝은 특정 주소·포트에서 연결을 기다리는 상태다.
- **이 과제:** Nginx 실행 여부와 TCP 80 리스닝 여부를 각각 확인한다.
- **주의:** 프로세스가 살아 있어도 외부 접속이 가능한 주소에 리스닝하지 않으면 접속이 실패할 수 있다.

### EBS · 이비에스 · Elastic Block Store

- **쉽게:** 빌린 컴퓨터에 연결하는 저장장치.
- **정확히:** EC2에 연결하는 블록 스토리지 볼륨. OS·웹 파일·로그 등을 저장한다.
- **이 과제:** 루트 볼륨을 사용하고 종료 시 삭제 설정 및 실제 삭제 여부를 확인한다.
- **구분:** EC2 종료와 모든 EBS 삭제는 같은 뜻이 아니다.

## 3. 네트워크 공간과 길

### Region / AZ · 리전 / 가용 영역

- **쉽게:** 리전은 큰 지역, AZ는 그 지역 안의 분리된 운영 구역.
- **정확히:** 리전은 AWS의 지리적 지역이고 AZ는 리전 내 격리된 인프라 구역이다.
- **이 과제:** 서울 `ap-northeast-2`를 사용한다. Subnet은 한 AZ에 위치한다.

### VPC · 브이피씨 · Virtual Private Cloud

- **쉽게:** 우리 서비스가 들어갈 전용 부지.
- **정확히:** AWS 안에 만드는 논리적으로 분리된 가상 네트워크.
- **이 과제:** `10.0.0.0/16` 주소 범위를 사용하도록 설계했다.

### Subnet / Public Subnet · 서브넷 / 퍼블릭 서브넷

- **쉽게:** VPC 부지 안에서 나눈 한 구역.
- **정확히:** VPC 주소 범위를 나눈 네트워크. IGW로 향하는 직접 경로가 있는 Subnet을 Public Subnet이라고 한다.
- **이 과제:** `10.0.1.0/24`에 EC2를 배치한다.
- **주의:** Public Subnet에 있다는 사실만으로 EC2가 공개되지는 않는다. IPv4 직접 인터넷 통신에는 퍼블릭 IP, 라우팅, 허용 규칙 등이 함께 필요하다.

### IGW · 아이지더블유 · Internet Gateway

- **쉽게:** VPC와 인터넷 사이의 출입구.
- **정확히:** VPC에 연결하는 인터넷 게이트웨이. 이 구성에서 EC2의 퍼블릭·프라이빗 IPv4를 매핑한다.
- **구분:** IGW는 VPC에 연결한다. Subnet에는 IGW를 대상으로 하는 라우트를 적용한다.

### Route · 라우트 / Routing · 라우팅

- **쉽게:** 라우트는 길 안내 한 줄, 라우팅은 그 안내에 따라 길을 정하는 일.
- **정확히:** 라우트는 목적지 주소 범위와 전달 대상의 조합이다.
- **예:** `0.0.0.0/0 → IGW`는 다른 더 구체적인 경로가 없는 IPv4 목적지의 트래픽을 IGW로 보내는 기본 경로다.
- **발음:** 그림에서 말하는 것은 보통 **라우트**다. ‘라운드’는 이 문맥의 네트워크 용어가 아니다.

### Route Table · 라우트 테이블

- **쉽게:** 길 안내판 여러 개를 모은 표.
- **정확히:** 목적지에 따라 전달 대상을 결정하는 라우트 집합.
- **이 과제:** Public Subnet에 연결해 인터넷 목적지의 기본 경로를 IGW로 지정한다.
- **구분:** 별도로 요청을 받아 처리하는 서버가 아니다. ‘어디로 보낼까’를 정하며, 접근 허용은 SG 등이 담당한다.

### Association / Attachment · 연결 관계

- **쉽게:** 설정을 만들기만 하지 않고 실제 사용할 대상에 붙이는 것.
- **이 과제:** Route Table과 Subnet의 association, IGW와 VPC의 attachment를 확인한다.
- **중요:** 다른 Subnet에 연결된 Route Table을 조회하면 내 서버의 경로를 증명할 수 없다.

## 4. 주소와 숫자 읽기

### IP / IPv4 · 아이피 / 아이피브이포

- **쉽게:** 컴퓨터의 네트워크 주소.
- **정확히:** IPv4는 32비트 주소 체계이며, 보통 `10.0.1.10`처럼 점으로 구분한 네 숫자로 표시한다.
- **구분:** IP는 주소이고, 포트는 그 주소에서 서비스를 구분하는 번호다.

### Public IP / Private IP · 퍼블릭 IP / 프라이빗 IP

- **쉽게:** 인터넷에서 사용하는 주소 / 내부 공간에서 사용하는 주소.
- **이 과제:** 방문자는 EC2의 Public IPv4로 접속하고 EC2 ENI에는 Private IPv4가 있다. IGW가 두 주소를 매핑한다.
- **주의:** 퍼블릭 IP가 있다고 모든 포트가 열리는 것은 아니다.

### CIDR · 사이더

- **쉽게:** 주소 하나가 아니라 주소의 범위를 적는 방법.
- **정확히:** `주소/접두사 길이`로 표기한다. IPv4의 접두사 길이는 앞에서 몇 비트를 네트워크 구분에 사용하는지 나타낸다.
- **예:** `/16`은 65,536개, `/24`는 256개, `/32`는 1개의 IPv4 주소를 포함한다.
- **주의:** 포함된 전체 주소 수와 AWS에서 실제 할당 가능한 주소 수는 다르다. 일반적인 AWS IPv4 Subnet에서는 5개 주소가 예약된다.

| 표기 | 읽는 법 | 이 과제에서의 뜻 |
| --- | --- | --- |
| `10.0.0.0/16` | 십 점 영 점 영 점 영, 슬래시 십육 | VPC의 사설 주소 범위 |
| `10.0.1.0/24` | 십 점 영 점 일 점 영, 슬래시 이십사 | 그 안의 Subnet 주소 범위 |
| `0.0.0.0/0` | 영 점 영 점 영 점 영, 슬래시 영 | 모든 IPv4 주소를 포괄하는 범위 |
| `<내 공인 IP>/32` | 내 공인 IP, 슬래시 삼십이 | 운영자 공인 IPv4 주소 하나 |

### `0.0.0.0/0`은 어디에 쓰느냐에 따라 해석이 다르다

| 위치 | 뜻 |
| --- | --- |
| Route Table 목적지 | 모든 IPv4를 포괄하는 기본 경로. 더 구체적인 경로가 우선 |
| SG 인바운드 소스 | 모든 IPv4 출발지에서 해당 프로토콜·포트 접근을 허용 |
| SG 아웃바운드 목적지 | 모든 IPv4 목적지에 해당 프로토콜·포트 통신을 허용 |

**`0.0.0.0/0` 자체가 모든 포트를 뜻하지는 않는다.** HTTP 80 규칙에 쓰면 모든 IPv4에서 80번으로 오는 통신을 허용한다.

### `0.0.0.0` 리스닝 주소는 다른 문맥이다

서버 설정이나 `ss` 출력에서 `0.0.0.0:80`은 **로컬의 모든 IPv4 인터페이스에서 80번 연결을 기다린다**는 뜻이다. CIDR `0.0.0.0/0`과 구분한다. 이 설정만으로 인터넷 접근이 허용되지는 않는다.

### DNS · 디엔에스

- **쉽게:** 이름으로 주소를 찾는 전화번호부.
- **정확히:** 도메인 이름을 IP 주소 등으로 해석하는 시스템.
- **구분:** IP 직접 접속이 되는데 도메인 접속만 실패하면 DNS도 점검한다.

## 5. 접근 제어와 서버 관리

### Port / TCP · 포트 / 티씨피

- **쉽게:** 한 컴퓨터 안에서 어떤 서비스로 갈지 구분하는 문 번호 / 연결해 데이터를 주고받는 통신 방식.
- **이 과제:** HTTP는 TCP 80, SSH는 TCP 22, 일반적인 HTTPS는 TCP 443을 사용한다.
- **구분:** SG에서 포트를 허용해도 그 포트에 서비스가 실행 중이어야 접속이 된다.

### SG · 에스지 · Security Group

- **쉽게:** 서버에 적용하는 출입 허용 규칙.
- **정확히:** ENI에 적용하는 상태 기반 가상 방화벽. 허용 규칙에 맞지 않는 새 연결은 허용하지 않는다.
- **이 과제:** TCP 80은 전체 IPv4에, TCP 22는 운영자 IP에만 허용한다.
- **구분:** SG가 별도 컴퓨터나 로그인 프로그램인 것은 아니다.

### SG 검사

- **쉽게:** ‘어디에서 왔고, 어떤 문으로 들어가려는가’를 규칙과 대조하는 것.
- **정확히:** 연결 상태와 적용된 SG 규칙을 바탕으로 트래픽 허용 여부를 판단하는 동작.
- **예:** 방문자의 TCP 80 요청은 허용하고, 허용 목록 밖 IP의 새 SSH 연결은 허용하지 않는다.
- **구분:** 웹페이지 내용이나 로그인 비밀번호를 검사한다는 뜻은 아니다. SSH 키 인증은 sshd에서 별도로 한다.

### Inbound / Outbound · 인바운드 / 아웃바운드

- **쉽게:** 서버로 들어오는 통신 / 서버에서 나가는 통신.
- **이 과제:** 방문자의 웹 요청은 EC2 기준 인바운드, EC2의 패키지 다운로드 요청은 아웃바운드다.
- **주의:** 서버의 웹 응답도 나가는 트래픽이지만, 서버가 새로 시작한 외부 요청과는 구분한다.

### Stateful · 상태 기반

- **쉽게:** 한 번 허용한 요청의 응답도 연결된 통신으로 처리하는 것.
- **정확히:** SG는 연결 상태를 추적해 허용된 요청의 응답 트래픽을 허용한다.
- **주의:** 반환 경로, NACL, OS 방화벽 등 다른 조건이 틀리면 응답이 실패할 수 있다.

### ENI · 이엔아이 · Elastic Network Interface

- **쉽게:** EC2에 연결된 가상 랜카드.
- **정확히:** VPC 안의 가상 네트워크 인터페이스. 프라이빗 IP와 SG 등을 가진다.
- **이 과제:** ‘SG를 EC2에 적용한다’는 설명을 더 정확히 표현하면 EC2의 ENI에 SG를 연결한다는 뜻이다.

### NACL · 네트워크 ACL

- **쉽게:** Subnet 구역 전체에 적용되는 별도의 출입 규칙.
- **정확히:** Subnet 수준의 상태 비저장 네트워크 접근 제어 목록. 허용·거부 규칙이 있고 응답 방향도 고려해야 한다.
- **이 과제:** 기본 NACL의 양방향 허용 상태를 전제로 설계하고 실제 배포에서 확인한다.

### SSH / sshd / Key Pair · 에스에스에이치 / SSH 서버 / 키페어

- **쉽게:** 서버에 안전하게 원격 로그인하는 방법 / 로그인을 받는 프로그램 / 인증에 쓰는 열쇠 쌍.
- **정확히:** SSH는 암호화된 원격 접속 프로토콜이고 sshd는 서버 데몬이다. 키페어의 공개키와 개인키로 인증할 수 있다.
- **이 과제:** SG가 운영자 IP의 22번 통신을 허용하고, sshd가 개인키에 대응하는 인증을 확인한다.
- **주의:** SG 허용과 SSH 인증은 서로 다른 단계다. 개인키는 공개 저장소와 로그에 넣지 않는다.

### IAM / 최소권한

- **쉽게:** 직원에게 업무에 필요한 권한만 주는 것.
- **정확히:** IAM은 AWS 주체의 작업 권한을 관리한다. 정책의 Action·Resource·Condition 등으로 필요한 범위를 제한한다.
- **구분:** IAM은 EC2 생성·삭제 같은 AWS 작업 권한이고 SG는 서버 통신 권한이다. 일반적인 SSH 키 로그인은 별도의 인증이다.

## 6. 웹 요청과 검증

### HTTP / HTTPS

- **쉽게:** 웹 요청과 응답의 약속 / TLS로 보호하는 웹 통신.
- **이 과제:** 필수는 HTTP 접속이며 HTTPS는 선택 과제다.
- **구분:** 443을 열기만 해서는 HTTPS가 완성되지 않는다. 인증서와 서버 TLS 설정 등이 필요하다.

### GET / URL / Endpoint · 겟 / URL / 엔드포인트

- **쉽게:** 정보를 달라는 요청 / 찾아갈 주소 / 기능을 호출하는 접점.
- **예:** `GET http://<퍼블릭IP>/health`는 해당 서버의 `/health` 경로에 정보를 요청한다.
- **구분:** `<퍼블릭IP>`는 실제 주소로 바꿀 자리 표시자이며 그대로 입력하는 문자가 아니다.

### `/`와 `/health` · 루트 경로와 헬스 경로

- **쉽게:** 첫 화면 주소 / 서버 상태를 확인하는 주소.
- **이 과제:** `/`는 웹페이지, `/health`는 200과 고정 본문 `OK`를 반환하도록 설정한다.
- **주의:** Nginx의 고정 응답은 해당 요청 처리 성공을 증명한다. 모든 프로그램과 DB까지 정상이라는 뜻은 아니다.

### HTTP 200 / 응답 본문

- **쉽게:** ‘요청을 정상 처리했다’는 번호 / 실제 답장 내용.
- **예:** 상태 코드는 `200`, 본문은 `OK`일 수 있다. 두 값을 각각 확인한다.

### localhost · 로컬호스트

- **쉽게:** 명령을 실행하는 컴퓨터 자기 자신.
- **예:** EC2 안에서 `http://localhost`를 요청하면 EC2 자신에게 요청한다.
- **주의:** 내 PC에서 같은 주소를 요청하면 내 PC를 가리킨다. 서버 내부 성공은 외부 접속 성공과 별도로 검증한다.

### curl · 컬

- **쉽게:** 터미널에서 웹 요청을 보내는 도구.
- **이 과제:** 응답 헤더·상태 코드·본문을 보존해 접속 증빙을 만든다.
- **주의:** curl 명령 종료 코드 `0`과 HTTP 상태 `200`은 다른 값이다. HTTP 오류를 명령 실패로 처리하려면 옵션도 고려해야 한다.

### Log / Access Log / JSON

- **쉽게:** 실행 기록 / 방문 요청 기록 / 이름과 값을 짝지어 저장하는 데이터 형식.
- **이 과제:** Nginx access log로 요청 처리를 확인하고 AWS 조회 JSON으로 설정을 확인한다.
- **주의:** 서버에 도달하지 못한 요청은 Nginx access log에 없을 수 있다. 로그가 없다는 사실 하나로 SG가 원인이라고 단정하지 않는다.

### Evidence ID · 증빙 실행 ID

- **쉽게:** 같은 실험의 기록을 묶는 이름표.
- **예:** `/health?evidence=run-001`을 요청하고 클라이언트 응답 기록과 access log의 `run-001`을 연결한다.
- **주의:** ID는 찾기 쉽게 연결하는 장치이며 단독으로 로그의 진위나 무결성을 보증하지 않는다.

### Troubleshooting · 트러블슈팅

- **쉽게:** 왜 안 되는지 증거로 좁혀가며 해결하는 과정.
- **이 과제:** 증상 → 가설 → 검증 → 조치 → 결과 → 재발 방지로 기록한다.
- **예:** 외부 접속 실패 → 내부는 200인지 확인 → 실제 SG·라우트 확인 → 원인 수정 → 같은 요청 재검증.

## 7. 정리와 비용

### Resource / Tag · 리소스 / 태그

- **쉽게:** 빌려 쓰는 자원 / 자원에 붙인 이름표.
- **이 과제:** EC2·EBS·VPC 등을 리소스 ID와 프로젝트 태그로 추적한다. 이름만으로 삭제 대상을 판단하지 않는다.

### Elastic IP · EIP · 탄력적 IP

- **쉽게:** 계정에 할당받아 관리하는 고정 퍼블릭 IPv4.
- **구분:** EC2에 자동 할당되는 퍼블릭 IP와 다르다. 이 기본 설계에서는 별도로 만들 필요가 없다.
- **정리:** 생성하지 않았으면 미생성을 기록하고, 생성했다면 연결 해제와 Release를 확인한다. 무료 여부는 현재 계정 조건과 요금을 확인한다.

### Stop / Terminate / Delete / Release

| 용어 | 쉬운 뜻 | 이 과제의 확인점 |
| --- | --- | --- |
| Stop | 컴퓨터 전원 끄기 | 인스턴스와 EBS 등이 남을 수 있어 정리 완료와 다름 |
| Terminate | EC2 인스턴스 종료 | 종료 완료 및 볼륨 삭제 여부 확인 |
| Delete | 자원 삭제 | 대상 리소스가 실제로 제거됐는지 확인 |
| Release | 할당 반납 | 할당받았던 EIP를 계정에서 반납 |

### Billing · 빌링

- **쉽게:** AWS 사용료 내역.
- **이 과제:** 자원 잔여 확인과 비용 내역 확인을 함께 수행한다.
- **주의:** 자원 삭제가 이미 발생한 비용을 없애지는 않는다. 요금 반영 시점과 크레딧 적용도 구분한다.

## 8. 이 순서로 읽어보자

1. **컴퓨터:** EC2 안에서 Nginx가 실행된다.
2. **공간:** EC2는 Public Subnet 안에, Subnet은 VPC 안에 있다.
3. **길:** IGW가 인터넷과 연결하고 Route Table이 전달 경로를 정한다.
4. **문:** SG가 HTTP와 SSH의 접근 범위를 나눈다.
5. **관리:** SSH로 서버를 관리하고 IAM으로 AWS 작업 권한을 관리한다.
6. **증명:** 외부 응답과 서버 로그 및 설정 조회를 연결한다.
7. **반납:** 만든 자원을 종료·삭제하고 남은 자원을 확인한다.

## 9. 트러블슈팅 보고서의 용어

EC2·VPC·SG·ENI·IAM·리전·JSON·로그는 위 절을 참고한다. 아래는 보고서와 수집 도구에서 추가로 사용하는 용어다.

| 용어 | 쉽게 말하면 | 이 사례에서의 의미 |
| --- | --- | --- |
| Console · 콘솔 | AWS 관리 화면 | 브라우저에서 자원을 설정하는 화면 |
| Session · 세션 | 로그인 상태 | 관리자와 실습용 IAM 사용자 `b3-1-lab` 로그인을 구분 |
| API | 프로그램의 요청 창구 | 콘솔·CLI가 AWS에 요청하는 작업의 인터페이스 |
| CLI | 글자로 명령하는 도구 | AWS 조회 결과를 파일로 수집 |
| GetSecurityGroupsForVpc | VPC에서 쓸 수 있는 SG 조회 | 이번 오류에서 누락됐던 작업 |
| Policy · 정책 | 작업 허가 규칙 | 누가 무엇에 어떤 작업을 할지 정의 |
| Inline policy | 사용자 등에 직접 넣은 정책 | B3-1-Seoul-Lab처럼 사용자에 포함된 정책 |
| Managed policy | 별도로 만들어 연결하는 정책 | 여러 사용자·그룹·Role에 연결 가능 |
| Caller / Principal | 요청한 주체 | 실제 API를 실행한 사용자·Role |
| Action | 작업 이름 | ec2:GetSecurityGroupsForVpc 등 |
| Resource | 작업 대상 | VPC 등 AWS 자원 |
| ARN | AWS의 정식 식별 주소 | 사용자·자원을 구분하는 문자열 |
| Effect / Allow / Deny | 규칙 결과 / 허용 / 거부 | 정책 문장의 판단 방식 |
| Condition | 적용 조건 | 리전 등 추가 조건 |
| aws:RequestedRegion | 요청한 AWS 리전 | 기존 Allow를 서울로 제한하는 조건 키 |
| Wildcard · 와일드카드 | 여러 이름을 가리키는 기호 | Describe*는 Describe로 시작하는 작업과 일치 |
| AdministratorAccess / FullAccess | 광범위한 관리·서비스 권한 | 이번 수정에서는 추가하지 않음 |
| Group | 권한을 묶는 사용자 모임 | 그룹을 통해 추가 정책이 적용될 수 있음 |
| SCP / 권한 경계 | 작업 권한의 상한 규칙 | 다른 Allow가 있어도 실제 작업을 제한할 수 있음 |
| Hypothesis · 가설 | 원인이라고 생각한 설명 | 확인된 사실과 구분해 검증 |
| Validation · 검증 | 근거로 맞는지 확인 | 오류·정책·응답을 대조 |
| 재검증 | 수정 뒤 같은 작업 확인 | 같은 사용자·리전·대상 API를 다시 호출 |
| Diff | 전후 변경 비교 | 추가한 Action 한 줄 표시 |
| Profile | 로컬 인증 설정 이름 | b3-1-lab 인증 묶음을 선택 |
| STS / get-caller-identity | 현재 요청자의 신원 확인 | 임시 자격 증명 관련 AWS 서비스의 호출자 조회 API |
| 임시 자격 증명 | 유효기간이 있는 인증 열쇠 | aws login으로 발급받는 로컬 개발 인증 |
| stdin / stdout / stderr | 입력 / 정상 출력 / 오류 출력 통로 | 수집기는 출력과 오류를 따로 보존 |
| Exit code | 명령 결과 번호 | 일반적으로 0은 성공. 응답 내용도 별도 확인 |
| UTC / KST | 공통 기준 시간 / 한국 시간 | KST는 UTC보다 9시간 빠름 |
| Run ID | 수집 실행 이름표 | AWS 요청 ID와 구분 |
| Request ID | AWS의 요청 식별자 | 실제 확보했을 때만 기록 |
| Manifest | 실행 기록 목록 | 명령·시각·종료 코드·파일을 묶은 JSON |
| PrimaryVpcId | SG를 생성한 기본 VPC의 ID | GetSecurityGroupsForVpc 응답에서 대상 VPC를 확인하는 필드 |
| IpPermissions | SG 인바운드 허용 목록 | 실제 포트·프로토콜·소스 확인 |
| SHA-256 / Hash | 파일 내용의 지문 | 저장 후 변경 여부 비교. 출처 진위 단독 보증은 아님 |
| Credentials | 인증 열쇠 | 비밀번호·Access Key·Secret Access Key·세션 토큰·개인키 등 |
| Debug | 상세 내부 동작 출력 | 수집기에서 사용하지 않음 |
| PASS / FAIL / INCOMPLETE | 통과 / 실패 / 미완료 | 해당 검사 범위의 결과이며 과제 전체 완료가 아님 |
| Masking | 공개할 사본에서 정보를 가림 | 원본과 별도로 민감한 식별정보를 가림 |
| Timeout | 대기 시간 제한 | 응답을 무한정 기다리지 않도록 제한 |

## 10. 쉘 스크립트와 자동화

| 용어 | 쉬운 뜻 | 이번 프로젝트에서의 역할 |
| --- | --- | --- |
| Shell · 쉘 | 글자로 명령을 받아 실행하는 프로그램 | Windows의 PowerShell, Linux의 Bash 등이 있음 |
| Shell script · 쉘 스크립트 | 여러 명령을 순서대로 적은 작업 지시서 | `infra/user-data.sh`가 Nginx 설치·설정·실행·검증을 수행 |
| Bash · 배시 | Linux에서 널리 쓰는 쉘 | 파일 첫 줄 `#!/bin/bash`가 사용할 실행 프로그램을 지정 |
| `.sh` | 쉘 스크립트에 흔히 붙이는 확장자 | 확장자만으로 실행되는 것이 아니라 지정한 쉘이 내용을 해석 |
| User data · 사용자 데이터 | EC2 첫 부팅에 전달하는 초기 작업 내용 | 작성한 Bash 스크립트를 EC2 안에서 실행. 로컬 PC에 Nginx를 설치하는 것이 아님 |
| Provisioning · 프로비저닝 | 필요한 서버·네트워크 등을 준비 | 이번에는 AWS 콘솔에서 수행. 전체 인프라 자동 생성 스크립트는 구현하지 않음 |
| Verification · 검증 | 결과가 조건에 맞는지 확인 | HTTP 응답·AWS 설정·서버 로그를 확인 |
| Cleanup · 정리 | 사용이 끝난 자원을 종료·삭제 | 체크리스트와 실제 ID를 기준으로 실행. 아직 전체 완료 전 |
| `.gitignore` | Git에 새로 추가하지 않을 파일 규칙 | 키·인증 설정·캐시 제외. 파일 삭제나 개인정보 마스킹은 하지 않음. 이미 추적된 파일은 별도 처리 필요 |

`user-data.sh`는 **Nginx 설치 → 설정 파일·웹페이지 작성 → 설정 문법 검사 → 서비스 실행 → 내부 /health 확인 → 로그 기록** 순서의 작업 지시서다. Python `.py` 수집기는 이와 다른 언어로 작성된 보조 도구다.
